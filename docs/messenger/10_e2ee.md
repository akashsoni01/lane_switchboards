# End-to-End Encryption (E2EE)

1:1 chat privacy using **vodozemac Olm** (Double Ratchet) and group chat using
**Megolm sender-keys**. The server never sees message plaintext.

## Protocol choice

| Layer | Choice | Rationale |
|-------|--------|-----------|
| 1:1 E2EE | Olm (vodozemac) | Audited Rust crate; Matrix/Signal-proven ratchet |
| Key agreement | X3DH-style prekey bundle | Async messaging; offline first message |
| Group E2EE | Megolm sender-keys | Encrypt once per group; distribute session key via Olm |

We do **not** hand-roll cryptographic primitives.

## What the server sees

| Data | Visible to server? |
|------|-------------------|
| Identity public keys | Yes (key directory) |
| One-time prekeys | Yes (consumed on fetch) |
| `ChatMessage.body` / `GroupMessage.body` | Opaque bytes only |
| Plaintext content | **Never** (when E2EE client is used) |

### 1:1 wire encoding

`ChatMessage.body` contains a prost-encoded [`EncryptedPayload`](../proto/messenger.proto):

- `sender_key` — sender Curve25519 identity (base64)
- `message_type` — `0` pre-key, `1` normal ratchet message
- `ciphertext` — Olm message bytes

### Group wire encoding

`GroupMessage.body` contains [`EncryptedGroupPayload`](../proto/messenger.proto):

- `session_id` — Megolm session id (Ed25519 pubkey, base64)
- `ciphertext` — `MegolmMessage` bytes

Sender-keys are distributed to members inside Olm-encrypted 1:1 messages as
[`GroupSessionKeyShare`](../proto/messenger.proto) prost blobs.

## Key lifecycle

```text
1. Client boots E2eeDevice (vodozemac Account)
2. PublishKeys(device_id) → multi-device key directory (home shard)
3. Sender: FetchKeys(peer [, device_id]) → KeyBundle → establish_outbound
4. send_encrypted_chat → body = EncryptedPayload
5. Receiver: decrypt_from_sender (creates inbound session on first pre-key msg)
6. One-time prekey removed from directory when handed out (FIFO, single-use)
7. RemoveDeviceKeys(device_id) revokes a device
```

### Multi-device

- Directory keyed by `(user_id, device_id)`; last publish per device wins.
- `FetchKeys.device_id` empty → most recently published device (monotonic seq).
- `KeyBundle.device_ids` lists all published devices for the peer.

### Persistence

| Backend | Config | Survives restart? |
|---------|--------|-------------------|
| Memory | default | No |
| Files | `ServerConfig.durable_dir` → `keys/{user}/{device}.json` | Yes |
| StorageNode | `ServerConfig.keys_storage` | Yes (when storage is durable) |

### Group sender-keys

```text
1. create_group_e2ee_session(group_id)
2. distribute_group_session_key → Olm encrypt GroupSessionKeyShare to each member
3. Members: try_import_group_key_from_chat on incoming 1:1 messages
4. send_encrypted_group → GroupMessage.body = EncryptedGroupPayload
5. decrypt_group on receive
```

### Safety numbers

`E2eeDevice::safety_number(local_identity, remote_identity)` returns a
stable hex fingerprint (sorted keys, SHA-256) for out-of-band verification.

## Client API

```rust
use lane_switchboards::messenger::{E2eeDevice, MessengerClient};

// 1:1
let mut e2ee = E2eeDevice::generate();
client.publish_e2ee_device("d1", &mut e2ee, 10).await?;
client.establish_e2ee_session("bob", &mut e2ee).await?;
client.send_encrypted_chat(&mut e2ee, "bob", "m-1", b"secret").await?;

// Group Megolm
MessengerClient::create_group_e2ee_session(&mut e2ee, "g-1");
client.distribute_group_session_key(&mut e2ee, "g-1", &["bob", "carol"]).await?;
client.send_encrypted_group(&mut e2ee, "g-1", "gm-1", b"group secret").await?;
```

## Cluster behaviour

- Key directory is homed on the user's hash shard (same as inbox).
- `PublishKeys` / `FetchKeys` / `RemoveDeviceKeys` forward to home; `KeyBundle`
  routes back via `for_user` and the location map.
- Ciphertext bytes are unchanged across peer hops.

## libolm cross-validation

Optional feature for CI environments with `cmake` installed:

```bash
cargo test --features libolm-compat --test libolm_compat
```

Tests verify vodozemac Megolm encrypt ↔ libolm decrypt and the reverse.

## Limitations

- No signed prekey rotation schedule (publish replaces device keys).
- Server cannot enforce E2EE; plaintext clients still work (migration path).
- Megolm forward secrecy requires periodic session rotation (not automated yet).
